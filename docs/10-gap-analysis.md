# 不足点チェックと発展計画

## 1. 結論

この案件パックには、要件、設計、Terraform、試験、運用、障害対応、証跡、面接説明までの一連の流れがあります。初心者向けポートフォリオの**設計教材**として必要な骨格はそろっています。

一方、採用担当者に「自分で構築し、確認し、改善した」と伝えるには、文書の追加よりも次の3点が重要です。

1. AWS 上で実行した、期待値と実測値付きの証跡
2. 失敗から原因を切り分けて直した記録
3. 設計判断を数値または比較表で説明した記録

未実施の項目は `NOT RUN` のままにし、設計したことと実行したことを混同しません。

## 2. 優先度別の不足点

### 必須: ポートフォリオを「実績」にする

| 不足点 | なぜ必要か | 初心者向けの完了条件 | 成果物 |
|---|---|---|---|
| 実環境の構築証跡 | コードがあることと、動くことは別だから | `plan` をレビュー後に `apply` し、account ID 等をマスクして保存 | plan、output、実施日時、終了コード |
| 全試験の実測 | 成功の判定根拠を示すため | ST-01〜ST-10 を `PASS/FAIL/BLOCKED` で記録 | 試験成績書、CLI 出力 |
| 障害訓練 | 正常構築だけでなく運用力を示すため | nginx 停止から検知・切離し・復旧までの時間を測る | タイムライン、原因、改善点 |
| 費用の実測 | AWS を安全に扱えることを示すため | 予算通知、利用時間、概算と実請求、削除後の残存確認を記録 | 費用表、destroy 確認 |
| 失敗・修正履歴 | 問題解決の過程が面接材料になるため | 1件以上について仮説、調査、修正、再試験を残す | issue または学習日誌、commit |

> AWS をまだ利用できない場合は、静的検査を完了させ、実環境項目を `NOT RUN` と明記した設計ポートフォリオとして公開します。架空の実測値を作ってはいけません。

### 次点: 再現性とレビュー品質を上げる

| 不足点 | 最小の追加内容 | 学べること |
|---|---|---|
| CI | Pull Request で `terraform fmt -check` と静的検査を自動実行 | 変更時の品質ゲート |
| Terraform の自動解析 | `tflint`、`tfsec` または `checkov` を1つ導入し、例外理由も記録 | 規約違反・設定不備の検出 |
| コスト見積り | lab/production の月額概算と、前提となる稼働時間・通信量を記載 | 構成と費用のトレードオフ |
| Decision Record | NAT 1台/2台、HTTP/HTTPS、local/remote state の比較を各1ページで記録 | 「なぜ選んだか」の説明力 |
| トラブルシュート表 | 症状→確認コマンド→正常値→次の分岐を整理 | 暗記ではない切り分け |

### 発展: 本番との差を埋める

以下は価値がありますが、最初から全部を追加すると学習範囲と費用が膨らみます。要件を1つ決め、設計、実装、試験、証跡を一巡させてから次へ進みます。

1. Route 53、ACM、HTTPS、HTTP から HTTPS へのリダイレクト
2. WAF、CloudTrail、AWS Config、GuardDuty、VPC Flow Logs
3. S3 remote state、暗号化、ロック、state への最小権限
4. SNS 通知と通知到達試験、担当・受付時間・エスカレーション
5. 負荷試験と SLI/SLO（可用性、応答時間、エラー率）
6. RTO/RPO を決めたバックアップ・復元試験（状態を持つ構成を追加する場合）
7. AMI/パッチ更新と Auto Scaling instance refresh の実測

## 3. 初心者が理解しやすい学習サイクル

各テーマを次の7項目で1枚にまとめます。サービス名を読むだけでなく、入力と結果を対応させる仕組みです。

1. **問い**: 何を解決するのか（例: なぜ EC2 に public IP が不要か）
2. **前提**: 必要な用語と構成図の該当箇所
3. **予想**: 操作前に期待値を書く
4. **操作**: Terraform または AWS CLI のコマンドを1つずつ実行
5. **観察**: 出力のどの値を見るかを明示
6. **説明**: 結果を「要件→設計→実装→試験」の順で自分の言葉にする
7. **復習**: 設定を1か所変えた場合の影響と戻し方を答える

分からない場合は、用語集に戻るだけでなく、構成図上で **From / To / Port / Route / Permission** の5点を書き出します。通信障害はこの順で確認すると、初心者でも調査範囲を狭めやすくなります。

## 4. 4段階の習得判定

| Level | できること | 判定課題 |
|---|---|---|
| 1 読める | 図を見て各リソースの役割を言える | 10語を自分の言葉で説明 |
| 2 追える | 通信経路と設定値をコードまで追える | 利用者から nginx までを From/To/Port 付きで説明 |
| 3 作れる | 手順に従い安全に構築・試験・削除できる | ST-01〜ST-10 と残存確認を実施 |
| 4 判断できる | 代替案、費用、障害点、戻し方を説明できる | lab と production の差を比較し、採用理由を説明 |

各 Level は「読んだ」ではなく、判定課題の出力または説明記録が残ったときに完了とします。

## 5. 推奨する追加順序

```text
静的検査
  → 予算アラートと作業ゲート
  → lab の plan / apply
  → ST-01〜ST-10 と障害訓練
  → destroy と請求・残存確認
  → 失敗記録を含む README 更新
  → CI / 自動解析
  → HTTPS
  → 通知試験
  → SLO / 負荷試験
  → 本番向け state・セキュリティ・バックアップ
```

この順序なら、機能を増やす前に「小さい構成を最後まで扱える」ことを証明できます。
